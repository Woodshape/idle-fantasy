Combat Data Unified Workflow

Create a small shared contract before the combat architecture extraction and data-driven skill configuration work split into parallel slices.

The goal is to keep behavior stable while separating action creation, ordered loadout priority, decision intent, and future data-backed content loading.

1 Short alignment pass before either large slice changes shared combat seams.
2 Parallel slices afterward: architecture extraction and data-backed configuration.
0 No Godot resource assets or encounter ownership extraction in this workflow.
Stable Existing bridge events and full-loop verification stay compatible.

Why This Exists

Conflict Reduction

Shared Hot Paths

  • CreateAdventurerActions
  • CreateMonsterActions
  • CreateHeavyStrike and CreateSpark
  • CombatActionRunner.SelectAction

Plan Mismatch

The architecture plan avoids a data-driven skill library in the same change, while the data plan replaces hardcoded action factories.

Shared Exit

Both slices can use a resolved ordered loadout of immutable runtime CombatAction objects.

Shared Contract

Behavior First

Runtime Actions

CombatAction remains the immutable object used by execution. Godot Resource definitions do not enter CombatActionRunner.

Loadout Source

A loadout source returns an ordered CombatLoadout. It can be hardcoded first and data-backed later.

Decision Policy

Decision code consumes a resolved loadout and target candidates. It should not construct action definitions.

Passive Identity

DefinitionId, CombatLoadoutId, and stable action ids can be additive bridge/state fields.

Unified Workflow

Before Split
  1. Inventory current hardcoded action creation, loadout ordering, selection behavior, and bridge output.
  2. Define the runtime action and ordered loadout contract while keeping CombatAction as the execution object.
  3. Wrap current warrior, mage, and slime hardcoded factories behind the loadout source without adding resources.
  4. Make decision intent consume resolved loadouts and preserve deterministic list-priority behavior.
  5. Add optional stable ids only as additive state or bridge fields when they can default to current behavior.
  6. Run dotnet build and scripts/verify_combat_main_loop.sh to prove parity.
  7. Split into architecture and data-backed configuration slices after the contract is stable.

Parallel Split

After Workflow

Architecture Slice Owns

  • CombatDecisionController
  • CombatTickResolver
  • CombatEncounter
  • encounter membership and end conditions
  • dynamic joins and multi-combatant verification

Data Slice Owns

  • CombatActionDefinition and CombatLoadoutDefinition
  • AdventurerDefinition and MonsterDefinition
  • GameContentLibrary
  • default data assets and validation
  • data-backed loadout resolution

Recommended order: unified workflow first, then data-backed loadouts and actor definitions, then architecture extraction. If multi-combatant behavior is the higher priority, architecture can go first after this contract exists.
