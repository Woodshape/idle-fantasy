Core Gameplay Roadmap

Next Gameplay Slices Plan

Build the smallest reliable path from the current warrior + mage + slime wave proof-of-concept into a readable idle RPG loop with progression, a town economy hook, player hiring, autonomous target choice, and hardened multi-combatant encounters.

The ordering is intentional: do not build shops, parties, or dungeon-like target selection until the starter loop is consistently watchable and verified.

Slice 1: Reliable Watchable Starter Loop

Foundation

Outcome

The current warrior + mage + three-slime wave is reliably fun and readable in headless verification and in the editor. Adventurers usually clear the first wave, take visible pressure, collect rewards, return/recover when appropriate, and see the wave respawn.

Implementation Notes

  • Prefer data edits in data/adventurers/*.tres, data/monsters/slime.tres, and data/spawns/default_world_content.tres.
  • Tune RestHealthRatio, RecoveryHealthPerSecond, slime Attack, MaxHealth, and AttackSpeedTicks first.
  • If randomness flakes, verify bounded outcomes rather than exact damage sequences.

Scope

  • Tune only existing warrior, mage, slime stats, rewards, spacing, and recovery.
  • Keep the first wave small.
  • Confirm slime melee behavior after mage ranged opener.
  • Confirm target selection, combat, loot, recovery, wave clear, and respawn.

Acceptance

  • scripts/verify_combat_main_loop.sh passes repeatedly.
  • Events include combat, loot, recovery, loop completion, wave clear, and respawn evidence.
  • State shows living adventurers after one completed loop.
  • Ranged mage behavior and slime melee response remain covered.

Slice 2: Adventurer Progression

Repeated Loops Matter

Outcome

XP creates clear level-up moments and small stat growth without class trees or build choices.

Minimal Model

  • xp_to_next_level = 20 + ((level - 1) * 15).
  • Increment Level, subtract threshold XP, then grow stats.
  • Suggested growth: MaxHealth +4, Attack +1, Defense +1 every other level.

Acceptance

  • Verification observes loot_collected and adventurer_level_up.
  • TestBridge state includes XP threshold fields.
  • HUD and state show level-up changes.

Implementation Notes

  • Put progression behavior on Adventurer, likely near AddRewards.
  • Emit adventurer_level_up with old/new level, XP before/after, threshold, and changed stats.
  • Update Adventurer.PublishState and GameController.UpdateAdventurerHud.

Slice 3: Town Gold Sink

Fight To Town Economy

Paid Healing First

  • Add one town service before inventory UI.
  • Spend adventurer gold at town when injured and able to pay.
  • If no gold, use existing slow recovery.
  • Emit town_service_used, gold_spent, and optionally town_service_unaffordable.

Potion Variant

  • Add PotionCharges to Adventurer, capped at 1.
  • Buy one potion in town if gold is available and none is carried.
  • Auto-use below a low HP threshold.
  • Emit potion_bought and potion_used.

Proposed Values

  • PaidRecoveryCost = 5.
  • PaidRecoveryHeal = 12.
  • Continue passive recovery if still injured.
  • Add Adventurer.SpendGold(int amount).

Acceptance

  • Gold decreases after town service use.
  • Events include town_service_used and gold_spent.
  • Broke adventurers still recover through adventurer_recovery_tick.
  • The main loop verifier stays green.

Slice 4: Manual Tavern Hiring

First Strategic Lever

Scope

  • Add a TestBridge command first; UI button can follow.
  • Cost gold from an explicitly chosen owner.
  • Spawn from existing AdventurerDefinition data.
  • Emit hire_requested, gold_spent, adventurer_hired, and hire_failed.

Currency Recommendation

Introduce a simple PlayerGold or TownGold counter on GameController before hiring. Keep adventurer personal gold for recovery unless design explicitly wants pooled party funds.

Acceptance

  • TestBridge can request a hire by definition id.
  • Gold decreases on successful hire.
  • New adventurer appears in game_loop.adventurer_count.
  • Broke hire emits hire_failed and does not spawn.
  • The main loop verifier stays green.

Slice 5: Target Choice And Risk

Autonomy

Scope

  • Add at least one additional monster tier or meaningful distance/reward distinction.
  • Score targets by distance, monster level/reward, adventurer level, and current HP ratio.
  • Emit target scoring details for TestBridge.
  • Add earlier retreat behavior for hurt adventurers.

Target Score

score = reward_value
  - distance_penalty
  - danger_penalty
  + level_fit_bonus
  + wounded_caution_adjustment

Readable Heuristics

  • reward_value = monster.GoldReward + monster.ExperienceReward.
  • distance_penalty = distance / 80.
  • danger_penalty = max(0, monster.Level - adventurer.Level) * 10.
  • Below 50% HP, prefer lower danger or return to town.

Acceptance

  • TestBridge shows at least two scored targets with different inputs.
  • Adventurers do not always pick nearest when reward/risk justifies it.
  • Hurt adventurers return earlier than healthy adventurers.
  • The main loop verifier stays green.

Slice 6: Encounter/Party Hardening

Before Real Parties

Scope

  • Make 1v2, 2v1, and 2v2 intentional single-encounter cases.
  • Prevent duplicate monster claims across active encounters.
  • Track reward membership explicitly.
  • Add reward splitting only after membership is reliable.

Implementation Notes

  • Treat CombatEncounter as the authoritative owner of membership.
  • Add encounter id, adventurer ids, monster ids, defeated monster ids, and eligible reward recipients.
  • Ensure social aggro and FindHuntTargets use the same ownership checks.

Acceptance

  • Verification covers 1v2, 2v1, and 2v2 starts as one encounter each.
  • No monster appears in two active encounters.
  • A defeated monster rewards only intended encounter membership.
  • Reward splitting is added only after ownership is stable.
  • The main loop verifier stays green.

Verification Strategy

Keep Baseline Fast

Always-Green Baseline

scripts/verify_combat_main_loop.sh

Avoid turning this into a slow exhaustive suite. It should remain the starter-loop acceptance test.

Focused Additions

  • Progression: adventurer_level_up and XP threshold state.
  • Town service: town_service_used, gold_spent, and fallback recovery.
  • Hiring: hire command/UI path, cost, and adventurer count increase.
  • Target choice: scoring events and non-nearest selection.
  • Encounter hardening: 1v2, 2v1, 2v2 ownership and rewards.

Recommended Order Of Work

Sequence
  1. Stabilize and tune the current starter loop until it is visually readable and green repeatedly.
  2. Add progression because it makes loop repetition meaningful with minimal new systems.
  3. Add a paid town recovery service because it connects earned gold back into survivability.
  4. Decide currency ownership, then add manual hiring through TestBridge first.
  5. Add risk-aware target choice once leveling and healing create meaningful risk/reward inputs.
  6. Harden encounter ownership before expanding real party behavior.

Key Design Decisions

Before Implementation

Open Questions

  • Should adventurer gold remain personal, or should combat loot feed a player/town treasury for hiring?
  • Should level-up heal the adventurer, partially heal, or only increase max health?
  • Should the first gold sink be paid healing or one carried potion?
  • Should hiring allow duplicate warriors/mages, or require unique definitions for now?
  • Should active combat retreat exist now, or only between fights first?

First Slice Exit Criteria

  • The mage clearly opens at range.
  • Slimes visibly pressure adventurers and attack at melee range.
  • Warrior and mage usually survive the starter wave.
  • Loot changes gold/XP.
  • Injured adventurers return and recover.
  • Cleared waves respawn.
  • The verifier proves those facts without flakes.
