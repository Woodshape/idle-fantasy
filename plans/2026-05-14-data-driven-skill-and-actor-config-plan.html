Implementation Plan

Data-Driven Skills And Actor Config

Move hardcoded combat actions, adventurer templates, monster templates, rewards, and default world composition into editable content assets while preserving the current tick-driven combat loop.

The recommended first implementation uses Godot Resource assets as the authoritative data format, with runtime actors and runners continuing to own mutable combat state.

Runtime Model

Resource Backed

CombatActionDefinition

Resource version of the current immutable CombatAction constructor: id, display name, kind, range, cooldown ticks, cast ticks, recovery ticks, action weight, damage multiplier, and target rules.

CombatLoadoutDefinition

Ordered list of action definitions. The list order becomes deterministic action priority for warriors, mages, and monsters.

CombatStatsDefinition

Starting values for max health, attack, accuracy, defense, evasion, initiative, and AttackSpeedTicks.

AdventurerDefinition

Template for level, stats, movement speed, stop distance, loadout, starting gold, starting experience, and sprite tint.

MonsterDefinition

Template for level, stats, rewards, movement, aggro distances, loadout, and display identity.

GameContentLibrary

Scene-assigned library that validates ids, resolves references, and creates runtime actions for controllers.

Boundary: data definitions describe initial values and available actions. Adventurer, Monster, and CombatActionRunner still own health, cooldowns, targets, aggro, cast state, and combat state.

Migration Flow

Keep Loop Playable
  1. Add resource classes for actions, loadouts, stats, adventurers, monsters, and default spawns.
  2. Add GameContentLibrary with validation and lookup dictionaries for stable ids.
  3. Create data assets that exactly match current hardcoded warrior, mage, slime, heavy_strike, and spark behavior.
  4. Add DefinitionId and setup helpers to Adventurer and Monster.
  5. Replace hardcoded default spawning in GameController with data-backed spawn entries.
  6. Replace hardcoded action factories with loadout resolution that returns immutable runtime CombatAction objects.
  7. Publish definition ids, loadout ids, and content validation events through TestBridge.
  8. Run build and bridge verification to prove the loop still reaches game_loop_completed.

Questions

Needs Review

Data Format

Recommended: Godot Resource assets now, optional JSON import later.

Choose between resources only, direct JSON loading, or resources plus later import tooling.

Basic Attacks

Recommended: model basic attacks as data actions, with cooldown from owner AttackSpeedTicks.

Decide whether ranged basic attacks are separate action assets or actor/loadout parameters.

Adventurer Identity

Recommended: move toward DefinitionId and ArchetypeId strings while keeping the enum temporarily.

Decide whether archetypes become pure data ids in this slice.

Spawn Granularity

Recommended: data-drive default arena spawns in the same slice.

Decide whether this slice covers templates only or full default world composition.

Validation Strictness

Recommended: fail fast for invalid required content during development.

Decide whether invalid data should stop spawning, skip entries, or fall back to code defaults.

Test Scenes

Recommended: support scalar overrides temporarily, but prefer definitions for new scenes.

Decide whether to migrate all current test scenes immediately.

Verification

Definition Of Done

Build And Loop

  • dotnet build passes.
  • scripts/verify_combat_main_loop.sh still passes.
  • Bridge run reaches game_loop_completed.

Bridge Evidence

  • Actor state includes definition_id.
  • Combat state includes loadout and action ids.
  • Validation emits bridge-visible success or failure events.
Acceptance Check
Skills and spells are data-defined. AdventurerCombatController no longer constructs heavy_strike or spark directly.
Actors are data-defined. Warrior, mage, and slime starting stats come from definitions.
Runtime state stays separate. Health, cooldowns, cast state, aggro, and targets remain on actors/runners.
Behavior parity holds. Representative combat events still include queue, cast, cooldown, aggro, loot, and loop completion.

Risks And Deferred Work

Scope Control

Risks

  • Godot C# resource exports may constrain nested array shapes.
  • Missing reference validation must be clear or data bugs will look like combat bugs.
  • Fallback scalar exports can become permanent if not removed later.

Deferred

  • Effect definitions, level scaling, equipment modifiers, and loot tables.
  • Recruitment pools, tavern hiring, and player spell library.
  • External content import/export and balance reports.
