First Playable Loop

First Game Loop Slice

An adventurer leaves the town, hunts a nearby monster, resolves probability-based combat, collects rewards, returns to the town, and becomes ready to repeat.

This validates the core simulation direction before adding shops, equipment, classes, dungeons, procedural world generation, or settlement upgrades.

Home Town marker, not a village or full settlement system.
Actor One pre-placed adventurer with separate intention and combat states.
Threat At least one simple monster target.
Combat Tick-based timing with explicit probability rolls.

Slice Scope

Small And Observable

Included

  • One town/home marker.
  • One autonomous adventurer.
  • One or more simple monsters.
  • A small top-down arena-style test scene, not a real world map.
  • Adventurer intention state machine.
  • Adventurer combat state machine.
  • Continuous movement.
  • Tick-based combat timing.
  • Probability-based combat rolls.
  • Basic travel, combat, rewards, death, and return-to-town.

Design Decisions Applied

From Design Doc
  • The first slice uses a town, not a village, as the home point.
  • Adventurer hiring is manual and costs player gold in the full design, but hiring UI is out of scope for this slice.
  • The slice starts with one pre-existing adventurer so the loop can be validated before adding recruitment.
  • Time is hybrid: movement is continuous, while combat and similar mechanics resolve on ticks.
  • There is no pause assumption for now; the slice should keep running.
  • Combat is random and should use explicit probability formulas followed by rolls.
  • The player is abstract and has no world avatar.
  • No real world map is needed yet. The slice only needs town, adventurer, and monster positions.
  • Far-away adventurer simulation is irrelevant for this slice.

Proposed Runtime Model

Simple Nodes First

Town

Node2D marker with service radius, display name, and return position.

Adventurer

Node2D or CharacterBody2D actor that owns identity, stats, inventory, position, and references to its controllers.

AdventurerController

Child Node or companion script that owns the high-level intention state machine, movement decisions, target selection requests, and return-to-town behavior.

AdventurerCombatController

Child Node or companion script that tracks detailed combat status, cooldowns, attack rolls, skills, spells, and conditions.

Monster

Node2D or Area2D with stats, reward values, and alive/dead state.

GameController

Owns high-level references, spawns initial actors, and provides target lookup.

Hud

Lightweight labels for adventurer state, gold, experience, and combat status.

Future Constraint

Expose movement and targeting through methods such as SetMoveTarget, SetCombatTarget, or RequestAction. AdventurerController can call those methods for AI behavior, while party leadership or a possession spell can later drive the same adventurer through the same action interface.

Adventurer AI State Machines

Two Layers

Use two distinct state machines so world decisions do not become tangled with combat details.

Intention State Machine

This high-level state machine lives in AdventurerController and tracks what the adventurer is trying to do in the game world.

  • IdleInTownWait briefly, then look for a target.
  • ChooseTargetAsk GameController for the nearest living monster appropriate for level.
  • TravelToTargetMove toward the monster.
  • FightMonsterHand detailed combat execution to the combat state machine until combat resolves.
  • CollectLootAdd gold and experience from the monster.
  • ReturnToTownMove back to the town.
  • RecoverInTownRestore health and prepare to loop again.
  • DeadStop acting and emit death event.

Reserved For Later

Possessed for player spell control, FindParty for seeking allies, and InParty for following party-level decisions.

Combat State Machine

This lower-level state machine lives in AdventurerCombatController and tracks detailed combat status while the intention state is FightMonster.

  • OutOfCombatNo active combat target.
  • EngagingCombat target selected, entering attack range or preparing first action.
  • ReadyCan choose the next combat action.
  • AttackCooldownWaiting for the next basic attack tick.
  • SkillCooldownWaiting for a skill cooldown before it can be used again.
  • CastingPreparing a spell or ability that resolves after a cast time.
  • RecoveringShort post-action recovery window.
  • DisabledStunned, rooted, feared, silenced, or otherwise unable to act.
  • DefeatedCombatant has reached zero health.

First Slice Combat Detail

The first slice only needs basic attack cooldowns, hit rolls, misses, damage, and death. Skills, spells, and conditions should be represented by the model shape but can remain stubbed until later.

Hit Formula Shape

hit_chance = clamp(base_hit_chance + attacker_accuracy - defender_evasion, min_hit_chance, max_hit_chance)
attack_hits = rng_roll_0_to_1 <= hit_chance

Damage On Successful Hit

damage = max(1, attacker_attack - defender_defense)

Implementation Steps

Build Order
  1. Create a simple game scene with root Node2D, town marker, one adventurer, one monster, and lightweight labels.
  2. Add Monster.cs with basic stats, ApplyDamage, and death/reward data.
  3. Add Town.cs with service radius, recovery behavior, and known return position.
  4. Add Adventurer.cs with identity, stats, gold, experience, current target references, controller references, shared action methods such as SetMoveTarget, SetCombatTarget, and ApplyDamage, plus shared TestBridge state publishing.
  5. Add AdventurerController.cs with high-level intention state machine, movement toward target positions, hunt target requests, combat delegation, bridge events, and state publishing.
  6. Add AdventurerCombatController.cs with combat state, attack cooldowns, hit chance rolls, successful-hit damage, and explicit future extension points for skills, spells, and conditions.
  7. Add GameController.cs with references to town, adventurer, and monsters, plus FindHuntTarget and loop completion detection.
  8. Wire the scene as the main scene or add a dedicated test scene. Prefer making the slice the main scene while the project is still early.
  9. Build both existing C# project files as required by the project workflow.
  10. Run a live TestBridge verification and observe event/state output until one loop completes.

Acceptance Criteria

Definition Of Done
  • The game starts into a visible top-down slice scene.
  • The scene contains a town marker, one adventurer, and at least one monster.
  • The adventurer autonomously leaves the town without player input.
  • The adventurer reaches a monster.
  • Combat starts on tick intervals.
  • The adventurer has a high-level intention state and a separate detailed combat state.
  • Each attack computes a hit chance and rolls against it.
  • Combat produces visible/logged hits, misses, and damage.
  • If the adventurer wins, the monster dies and rewards are added.
  • The adventurer returns to the town.
  • The adventurer recovers and can begin another hunt.
  • If the adventurer dies, the state becomes Dead and the loop stops for that adventurer.
  • TestBridge emits enough events/state to verify the loop without relying only on visuals.

Risks And Constraints

Keep It Tight
  • Avoid overbuilding the architecture before the loop is fun to watch.
  • Keep the boundary clear: intention state decides goals, combat state resolves moment-to-moment combat.
  • Keep combat formulas explicit and log rolled values so failures are diagnosable.
  • Do not introduce inventory, shops, or procedural generation in this slice.
  • Do not build a real world map yet; simple positioned nodes are enough.
  • Do not add hiring UI yet; start with one pre-placed adventurer.
  • The current PlayerController may become obsolete or should be treated as an input/movement prototype.
  • Avoid coupling click-to-move directly to the old PlayerController; future possession should drive adventurer actions through the same action interface used by AI.
  • Party logic should not be added until the solo loop has clean target selection, rewards, and return behavior.
  • The scene structure should stay simple enough to inspect manually in Godot.
