Current Code Behavior

Encounter and Join Mechanics

This document describes the current adventurer and monster encounter model implemented by AdventurerController, AdventurerCombatController, CombatActionRunner, GameController, and Monster. An encounter is an active set of living adventurers, living monsters, and combat runners advanced by the shared simulation tick.

Initial Encounter Formation

  1. The adventurer chooses hunt targets. In ChooseTarget, the controller clears its previous encounter list and calls GameController.FindHuntTargets(adventurer, MaxEncounterMonsters).
  2. The game filters monsters. Only living monsters are eligible. Monsters already targeted by another living adventurer's CurrentMonsterTarget are excluded. Remaining monsters are sorted by distance to the adventurer and capped by MaxEncounterMonsters.
  3. The adventurer walks to the first selected monster. The first selected monster becomes CurrentMonsterTarget. The opening approach distance uses the longest target-requiring adventurer action range, with MeleeApproachDistance as the minimum.
  4. Combat starts after arrival. When the adventurer reaches the approach point, UpdateFight builds the encounter adventurer list with FindEncounterAdventurers and starts combat with the selected living monsters.
  5. The combat controller creates runners. StartCombat filters dead combatants, removes duplicates, clears prior combat, increments the encounter id, and creates one CombatActionRunner for each adventurer and monster in the encounter.

Scene overrides matter. The default AdventurerController.MaxEncounterMonsters is 1, but current test scenes such as TestCombat1v2.tscn and TestCombat2v2.tscn override it to 2.

Targeting Rules

Adventurer Target Selection

An adventurer runner selects the nearest living monster in the active encounter. If its current target dies or disappears, TrySelectTarget can switch it to another living encounter monster.

Monster Target Selection

A monster runner prefers its living AggroTarget when that target is one of the encounter adventurers. If that is not valid, it selects the nearest living encounter adventurer.

Proximity Aggro

Every monster is checked for proximity aggro once per simulation tick from GameController._PhysicsProcess, when the shared simulation clock advances. A monster that already has a living aggro target skips the initial proximity scan.

  1. The monster finds the nearest living adventurer from GameController.Adventurers.
  2. If the distance to that adventurer is greater than the monster's AggroRange, nothing changes.
  3. If the adventurer is inside AggroRange, the monster calls SetAggroTarget(adventurer, "", "proximity", currentTick).
  4. The monster immediately asks the game to add it to the adventurer's active encounter through TryAddAggroMonsterToEncounter.
  5. On each later simulation tick, a monster with an existing living aggro target retries the encounter-join request. This covers the case where the monster acquired aggro before the target's combat encounter existed.

Social Aggro

Adventurer combat runners are constructed with an aggro callback. After a target-requiring action resolves, CombatActionRunner.NotifyMonsterAggro calls AdventurerCombatController.ApplySocialAggro.

Current behavior is resolution-based, not hit-only. The callback runs after any target-requiring action resolves, even if the action missed or dealt no damage. The target monster still must be alive for social aggro to propagate.

  1. The primary target receives aggro_trigger = "ability_resolved" and the action id.
  2. Other living monsters already inside the same encounter receive aggro_trigger = "social_aggro" and the same action id.
  3. The controller also asks GameController.ApplySocialAggro to inspect world monsters outside the current encounter.
  4. A world monster socially aggros when it is living, is not the source monster, and is within its own AggroRange of the source monster.
  5. Eligible world monsters are assigned the same adventurer target and then routed through TryAddAggroMonsterToEncounter.

Dynamic Monster Joins

GameController.TryAddAggroMonsterToEncounter finds an active AdventurerCombatController whose EncounterAdventurers contains the aggro target. It then delegates to AdventurerCombatController.TryAddAggroMonster.

Condition Required State
Encounter active The target adventurer must belong to an active encounter controller.
Monster state The joining monster must be alive.
Adventurer state The aggro target must be alive and already listed in the encounter adventurers.
Already in encounter The monster only refreshes its aggro target. No new runner or join event is created.
New to encounter The monster is added to EncounterMonsters, receives a monster runner, starts at the current tick, and emits monster_joined_encounter.

Encounter Completion

Each simulation tick, the combat controller advances all runners, queues actions, resolves rolled actions, handles deaths, and publishes encounter state. The encounter remains active while at least one adventurer and one monster in the controller are alive.

  • When a monster dies, monster_defeated is emitted once for that monster id.
  • When the current target dies, the adventurer can switch to the controller's current living monster target.
  • If the controller still has living monsters, AdventurerController stays in FightMonster.
  • When no living monsters remain, the adventurer transitions to CollectLoot.

Bridge Events

Event Meaning
adventurer_target_selected Initial hunt target list was selected; includes monster_count.
combat_started Encounter controller created the active encounter; includes adventurer and monster names and counts.
monster_aggro_target_set A monster target changed; includes aggro_trigger, distance, and aggro range data.
monster_joined_encounter A living monster was dynamically added to an active encounter and received a runner.
combat_target_changed A runner selected a new target because combat started or the previous target became unavailable.
combat_tick_started / combat_tick_completed Simulation tick boundaries for the encounter, including living combatant counts.

Tuning Knobs

MaxEncounterMonsters

Controls how many monsters the adventurer intentionally selects before combat starts. Default is 1; scenes can override it.

MaxEncounterAdventurers

Controls how many living adventurers are included in the initial encounter, ordered with the leader first and then by distance to the leader.

AggroRange

Used by proximity aggro and social aggro distance checks. Social aggro compares the candidate monster's distance to the source monster against the candidate monster's own range.

AggroAttackDistance

The stopping distance for monsters moving toward their aggro target.

Current Caveats

  • Social aggro is currently action-resolution based. If hit-only social aggro is desired, the callback needs to check ActionResolution.Hit before calling NotifyMonsterAggro.
  • Dynamic joins update AdventurerCombatController.EncounterMonsters, but AdventurerController still keeps its own initial _encounterMonsters list for loot collection. Reward handling for dynamically joined monsters should be reviewed before relying on dynamic-only joins for full game-loop completion.
  • TryAddAggroMonsterToEncounter chooses the first active encounter containing the aggro target. It does not currently reject a monster that may already be represented by another active encounter controller.
  • Initial hunt selection prevents selecting monsters claimed by another adventurer's CurrentMonsterTarget, but dynamic proximity and social aggro paths do not use that claim filter.
